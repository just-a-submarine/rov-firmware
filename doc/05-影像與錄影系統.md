## 二、影像傳輸方案：手機直連 ROV

ESP32 SoftAP 預設不啟用 AP Isolation，同一 AP 下的 STA 之間可直接互通（Layer-2 硬體轉發）。手機（192.168.4.x）可直接存取 ROV（192.168.4.100）的 HTTP Server，地面站零 CPU 負擔。

```html
<!-- 手機網頁中只需這一行 -->
<img src="http://192.168.4.100:80/stream"
     style="width:100%; max-height:40vh; object-fit:contain;">
```

### 各方案比較

| 評估項目 | 方案 A：地面站中繼 | **方案 B：直連 ROV（採用）** | 方案 C：ESP-NOW |
|---------|-----------------|--------------------------|--------------|
| 地面站 CPU | 極重 | **零** | 極重 |
| Wi-Fi 頻寬 | 2× | **1×** | 不可行 |
| 延遲 | +50–150ms | **最低（單跳）** | 數百 ms |
| VGA@15fps | 勉強 | **輕鬆** | 完全不可行 |

方案 C 不可行原因：ESP-NOW unicast 實測吞吐約 350KB/s，VGA JPEG 每個影格 30–50KB 需 120–200 個封包，理論影格率不到 5fps，且任一封包遺失整個影格作廢。

## 三、串流模式總表

| 模式 | 觸發 | 串流解析度 | 影格率 | Wi-Fi 串流 | SD 錄影 | LB 即時拍照 |
|------|------|-----------|------|-----------|---------|------------|
| 0 純串流（預設） | 開機 / RB 切回 | VGA 640×480（固定） | ~6–7 FPS | ✅ | — | ✅ 可用 |
| 1 串流 + SD 錄影 | RB 切換 | VGA 640×480（固定） | ~6–7 FPS | ✅ | ✅ | ❌ 鎖定 |

RB 鍵邊緣觸發，在模式 0 / 1 之間切換。ROV 切換後經 TelemetryPacket 回傳確認。

> **影格率現況**：XCLK 採 10MHz（20MHz 會出垂直條紋，見 §五）→ pixel clock 為瓶頸，VGA 實測約 6–7fps。
> 解析度不隨 RSSI 切換（只調 JPEG 壓縮率），避免切換造成卡頓（見 §四）。

### 解析度分工

| 功能 | 解析度 | 決定依據 |
|------|--------|---------|
| 串流（兩種模式均適用） | 640×480（VGA，固定） | 不隨 RSSI 切換解析度，只調 JPEG 壓縮率 |
| LB 即時拍照 | 等同當前串流尺寸（VGA） | 直接存最新串流影格，不切解析度、不暫停 |

### 模式 1 拍照鎖定原因

即時拍照雖不切解析度，但錄影中 SD 連續寫入已幾乎佔滿 SDMMC 頻寬（最高約 2MB/s），再插入單張影格寫檔會干擾
.avi 時序、造成影格緩衝溢位。故模式 1 鎖定拍照（程式上 `takePhotoInstant` 僅在模式 0 執行）。

## 四、RSSI 降級邏輯（固定 VGA + 遲滯，只調壓縮率）

| 等級 | 進入條件（帶遲滯） | 動作（解析度固定 VGA） |
|------|------------------|----------------------|
| 0 一般 | 由等級1回升：RSSI > −64 | JPEG quality 10（畫質較好），串流開 |
| 1 弱 | RSSI ≤ −70 進入 | JPEG quality 14（更壓縮省頻寬），串流仍開（不暫停） |
| 2 極弱 | RSSI ≤ −86 進入；> −82 回到等級1 | 暫停串流，等待回升 |

**為何這樣設計**：舊版「依 RSSI 動態切換 SVGA/VGA」會在門檻附近反覆切換解析度，每次切換相機都要重設 →
畫面「自己頓住又活過來」。改為**解析度固定 VGA、只調 JPEG 壓縮率**，並對等級轉移加**遲滯**
（降級早、升級需更強訊號），只有訊號極弱（< −86dBm）才暫停串流。

```cpp
// 固定 VGA，只隨訊號調壓縮率；只有極弱才暫停。轉移帶遲滯避免抖動。
void applyQualityIfChanged() {
    static int band = 0;            // 0=一般 1=弱 2=極弱（皆維持 VGA）
    int8_t rssi = g_rssi;
    int prev = band;
    switch (band) {
        case 0: if (rssi <= -70) band = 1;                                 break; // 一般→弱
        case 1: if (rssi >  -64) band = 0; else if (rssi <= -86) band = 2; break; // 弱↔一般／弱→暫停
        case 2: if (rssi >  -82) band = 1;                                 break; // 暫停→弱（回升）
    }
    if (band == prev) return;

    sensor_t* s = esp_camera_sensor_get();
    if (!s) return;
    if      (band == 0) { s->set_quality(s, 10); g_streamActive = true; }
    else if (band == 1) { s->set_quality(s, 14); g_streamActive = true; }
    else                { g_streamActive = false; }   // 極弱才暫停
}
```

### 相機調參（極簡原則）

只動兩個旋鈕，其餘全交 OV5640 原廠自動預設：

```cpp
sensor_t* s = esp_camera_sensor_get();
if (s) {
    s->set_brightness(s, 2);   // 亮度 +2（水下偏暗補償）
    s->set_contrast(s, -1);    // 對比 -1（降低水下高對比雜訊）
}
```

> ⚠ **不要整包覆蓋 OV5640 原廠值**——自動曝光（AEC）、自動白平衡（AWB）、自動增益（AGC）
> 等皆保持原廠預設，僅微調亮度與對比即可。過度調參反而在不同水深 / 光源下適應力更差。

## 五、攝影機初始化（Freenove N16R8 腳位）

```cpp
#include "esp_camera.h"

void setupCamera() {
    camera_config_t config;
    config.pin_xclk    = 15;  config.pin_sccb_sda = 4;
    config.pin_sccb_scl = 5;
    config.pin_d0 = 11; config.pin_d1 = 9;  config.pin_d2 = 8;
    config.pin_d3 = 10; config.pin_d4 = 12; config.pin_d5 = 18;
    config.pin_d6 = 17; config.pin_d7 = 16;
    config.pin_vsync = 6; config.pin_href = 7; config.pin_pclk = 13;
    config.pin_pwdn  = -1; config.pin_reset = -1;

    config.xclk_freq_hz  = 10000000;            // 10MHz：20MHz 會因 FPC 排線訊號完整性出垂直條紋（見下方）
    config.pixel_format  = PIXFORMAT_JPEG;
    config.frame_size    = FRAMESIZE_VGA;       // 開機預設 640×480（流暢優先：小幀、低延遲、弱訊號容錯）
    config.jpeg_quality  = 10;
    config.fb_count      = 3;                    // 多一個緩衝平滑抖動（配 GRAB_LATEST 仍低延遲）
    config.fb_location   = CAMERA_FB_IN_PSRAM;
    config.grab_mode     = CAMERA_GRAB_LATEST;
    config.ledc_timer    = LEDC_TIMER_3;        // 相機 XCLK 用獨立 timer/channel，避開馬達 LEDC（ch0–5/timer0）
    config.ledc_channel  = LEDC_CHANNEL_7;

    esp_camera_init(&config);

    // 畫面方向修正（模組實裝上下顛倒）：VFLIP=1；若同時左右鏡像再把 HFLIP 設 1（＝旋轉 180°）。
    sensor_t* s = esp_camera_sensor_get();
    if (s) { s->set_vflip(s, 1); s->set_hmirror(s, 0); }   // 對應 config.h 的 CAM_VFLIP / CAM_HFLIP
}
```

> **XCLK 頻率 vs 垂直條紋（FPC 排線限制）**：相機接於 FPC 排線。XCLK 拉到 20MHz 時 PCLK 隨之提高，
> 排線高速下訊號完整性不足 → 並列資料線位元錯誤 → 畫面出現**垂直條紋**（非掉幀，影格數正常）。
> 降回 **10MHz** 畫面乾淨，代價是幀率降到 ~6–7fps。要在 20MHz 跑乾淨需換更短/更好的排線或改善接觸/焊接。

> **MJPEG 伺服器用 ESP-IDF 內建 `esp_http_server`**（非 ESPAsyncWebServer）——CameraWebServer 同款做法、
> 最穩定。串流端點 `:80/stream`（multipart/x-mixed-replace）；ROV 端不需 ESPAsyncWebServer/AsyncTCP。

### 相機容錯（持續背景重試自癒，2026-06-06 起）

OV5640 的 **PWDN/RESET 腳未接**（config `-1`）→ 上電/重置無法由晶片控制，**冷啟動是非決定性的**：
同一硬體每次開機落在略微不同狀態，常需多次 `deinit+init` 才吐得出第一幀（讀得到 PID 0x5640 但
`fb_get` 一開始回 null）。串流任務的容錯：

1. **開機探幀**：抓到首幀就正常開跑；抓不到設 `g_camDead` 進背景重試（不再「試 3 次就判死」）。
2. **執行期掉幀自癒**（水下不重開機）：影格序號連續 ~4s 沒推進 → 設 `g_camDead` 轉入背景重試。
3. **背景重試自癒（取代舊的永久判死）**：`g_camDead` 為真時持續 `reinitCamera()`（退避 1→5s），
   相機一吐出影格就自動清旗標、串流續傳——**不必拔電**。期間 `streamHandler` 回 500 讓手機 `<img>`
   顯示「影像中斷，重連中」每 3s 重連，相機復原後自動接上。streamTask 為最低優先級，重試**不影響控制/遙測**。

> 實證（2026-06-06）：冷啟動 wedge（`cam` 凍在 84）→ 背景重試後自動恢復、`cam` 一路爬到 800+ 不再凍，全程未拔電。
> **「同硬體時好時壞、有時要等十幾秒才有畫面」＝這個非決定性冷啟動 × 需要的 reinit 次數**：0–1 次→秒開、
> 2–3 次→等很久、舊韌體 >3 次→直接放棄全黑。
> 治本仍是硬體：FPC 接觸弄紮實可減少需重試次數（開更快）；要秒開零凍需把 PWDN/RESET 焊到空閒 GPIO 讓軟體能主動重置 sensor。

## 六、即時拍照（LB 鍵，純串流模式下有效）

```
LB 鍵在地面站端邊緣觸發 → takePhoto = true（單次脈衝）→ ControlPacket 傳至 ROV
    ↓
模式 0：直接把「目前串流的最新影格」寫入 SD（不切解析度、不暫停串流）→ 零延遲、不中斷畫面
模式 1：忽略（SD 正在錄影，鎖定）
```

改為**即時拍照**：不再切到 720p、不暫停串流。直接複製串流任務目前發佈的最新 JPEG 影格寫入 SD，
解析度等同當前串流尺寸（VGA）。好處是手機畫面完全不卡頓、拍照零延遲。

### ROV 端實作

```cpp
// 串流任務每輪：若有拍照請求且為模式 0，即時存最新影格（不暫停、不切解析度）
void takePhotoInstant() {
    g_photoReq = false;
    if (!recorderIsCardReady()) return;

    // 從共享影格緩衝複製最新一張（與串流 handler 共用，mutex 保護）
    size_t len = 0;
    xSemaphoreTake(g_frameMutex, portMAX_DELAY);
    len = g_frameLen;
    if (len > 0 && len <= MAX_JPEG) memcpy(photoBuf, g_frameBuf, len);
    else len = 0;
    xSemaphoreGive(g_frameMutex);
    if (len == 0) return;                          // 還沒有可存的影格

    char fn[40];
    snprintf(fn, sizeof(fn), "/photo_%lu.jpg", (unsigned long)millis());
    File f = SD_MMC.open(fn, FILE_WRITE);
    if (f) { f.write(photoBuf, len); f.close(); }
    g_photoAck = true;                             // 下一個遙測週期回傳拍照確認
}
```

拍照確認經 `TelemetryPacket.photoAck` 回傳，手機顯示「📷 已拍照存檔」Toast。LB 的邊緣觸發在**地面站端**處理
（按一下送一張），ROV 端收到 `takePhoto` 即存當前影格。

### 🚨 已知問題：拍照延遲 / 需連按（待修）

手機 25Hz（`controlTick` 40ms）取樣送出當下 bit，<40ms 的點擊在兩次 tick 間
set→clear 不被取樣 → GS 收不到上升邊緣。

**修法**：動作鍵加最短脈衝寬（~120ms），保證 25Hz 上行必取樣到。

另 `takePhotoInstant` 即使 SD 寫檔失敗也設 `photoAck=true`（假「已存檔」提示）→
改為**只有實際寫檔成功才設 ack**。

## 七、SD 錄影（AVI MJPEG 格式）

### 錄影格式要求

錄影寫入 `.avi` 檔案，必須遵循完整的 **RIFF/AVI 容器格式**，否則播放器無法解析。直接把 JPEG 影格 raw bytes 連續寫入然後命名成 `.avi` 是**不可播放的**。

### AVI MJPEG 容器結構

```
RIFF 'AVI '
  ├── LIST 'hdrl'          ← AVI 主標頭
  │     ├── 'avih'         ← 主標頭（影格率、影格寬高、串流數）
  │     └── LIST 'strl'    ← 串流標頭
  │           ├── 'strh'   ← 串流標頭（fccType='vids', fccHandler='MJPG'）
  │           └── 'strf'   ← 串流格式（BITMAPINFOHEADER）
  ├── LIST 'movi'          ← 影像資料區
  │     ├── '00dc' + JPEG 影格 1
  │     ├── '00dc' + JPEG 影格 2
  │     ├── ...
  │     └── '00dc' + JPEG 影格 N
  └── 'idx1'               ← 索引區（每個影格的偏移量與大小）
```

### 實作流程

1. **開始錄影**：寫入 RIFF 標頭 + hdrl（影格率設 15、解析度 640×480、codec MJPG），此時總大小欄位先填 0
2. **每個影格寫入**：每個 JPEG 影格前加 `'00dc'` chunk header（4 bytes tag + 4 bytes size），同時記錄該影格在檔案中的偏移量與大小（存於 RAM 陣列，供 idx1 使用）
3. **結束錄影**：寫入 `idx1` 索引區，回頭更新 RIFF 標頭的總大小欄位，關閉檔案

### 關鍵程式碼框架

```cpp
File aviFile;
uint32_t frameCount = 0;
uint32_t moviOffset = 0;

// 索引暫存（每個影格 16 位元組：4 tag + 4 flags + 4 offset + 4 size）
// 15fps × 60s × 30min ≈ 27000 影格 × 16 位元組 ≈ 432KB，需存在 PSRAM
struct AviIdx {
    uint32_t offset;
    uint32_t size;
};
AviIdx* idxBuffer;  // ps_malloc() 分配

void startRecording() {
    char filename[32];
    sprintf(filename, "/rec_%lu.avi", millis());
    aviFile = SD_MMC.open(filename, FILE_WRITE);

    // 分配索引緩衝（PSRAM）
    idxBuffer = (AviIdx*)ps_malloc(sizeof(AviIdx) * 30000);
    frameCount = 0;

    // 寫入 RIFF + hdrl（固定結構，約 224 位元組）
    writeAviHeader(aviFile, 640, 480, 15);  // 寬、高、影格率
    moviOffset = aviFile.position();

    // 寫入 LIST 'movi' 標頭（大小先填 0，結束時回補）
    aviFile.write("LIST", 4);
    uint32_t placeholder = 0;
    aviFile.write((uint8_t*)&placeholder, 4);
    aviFile.write("movi", 4);
}

void writeFrame(camera_fb_t *fb) {
    if (!aviFile || !fb) return;

    // idx1 偏移須對齊 'movi' FourCC（moviOffset 指 "LIST"，+8 跳過 "LIST"+size 到 'movi'）。
    // 舊式 `- moviOffset - 4` 每筆多 +4、指進 JPEG 長度欄 → 信任索引的播放器整支黑（見下方「已修正」）。
    uint32_t frameOffset = aviFile.position() - (moviOffset + 8);
    uint32_t paddedSize = (fb->len + 1) & ~1;  // RIFF 要求偶數對齊

    // 寫 chunk header
    aviFile.write("00dc", 4);
    aviFile.write((uint8_t*)&fb->len, 4);
    aviFile.write(fb->buf, fb->len);
    if (fb->len & 1) aviFile.write((uint8_t)0);  // padding

    // 記錄索引
    if (frameCount < 30000) {
        idxBuffer[frameCount].offset = frameOffset;
        idxBuffer[frameCount].size   = fb->len;
    }
    frameCount++;
}

void stopRecording() {
    if (!aviFile) return;

    // 回補 LIST 'movi' 大小
    uint32_t moviSize = aviFile.position() - moviOffset - 8;
    aviFile.seek(moviOffset + 4);
    aviFile.write((uint8_t*)&moviSize, 4);
    aviFile.seek(0, SeekEnd);

    // 寫入 idx1，做防禦性邊界檢查防止越界讀取 PSRAM 造成當機
    uint32_t safeFrameCount = (frameCount > 30000) ? 30000 : frameCount;
    writeIdx1(aviFile, idxBuffer, safeFrameCount);

    // 回補 RIFF 總大小
    uint32_t fileSize = aviFile.position() - 8;
    aviFile.seek(4);
    aviFile.write((uint8_t*)&fileSize, 4);

    aviFile.close();
    free(idxBuffer);
    idxBuffer = nullptr;
}
```

### 串流 + 錄影同步邏輯

```cpp
void streamTask(void *pvParam) {
    while (true) {
        camera_fb_t *fb = esp_camera_fb_get();
        if (!fb) { vTaskDelay(10); continue; }

        // Wi-Fi 串流（永遠執行）
        if (streamActive) sendMJPEGFrame(fb);

        // SD 錄影（僅模式 1 開啟時）
        if (streamRecord) writeFrame(fb);

        esp_camera_fb_return(fb);
        vTaskDelay(1);
    }
}
```

### ✅ 已修正：idx1 偏移錯誤（2026-06-07）

`recorder.cpp` 的 `writeFrame` 中 `frameOffset` 計算原先每筆 +4，
導致 idx1 條目指向 JPEG 長度欄而非 `00dc` 標記。
信任索引的播放器（Windows Media Player 等）會全黑；
ffmpeg/VLC 靠重掃 movi chunk 才能播。

**已修正**：`frameOffset = position - (g_moviOffset + 8)`（對齊 'movi' FourCC + size），
現在 idx1 偏移正確指向 `00dc` 標記。

## 九、任務排程優先級（影像必須讓位給控制／遙測）

相機 MJPEG 由 ESP-IDF `esp_http_server` 服務，與 ESP-NOW 控制/遙測共用**同一顆 Wi-Fi（Core0）**與
**同一條 2.4GHz 頻道**（經地面站 AP 轉發＝雙倍 airtime）。若不約束，串流會把控制/遙測卡住、操控延遲。

**FreeRTOS 優先級／核綁定（`startControlTasks` / `startHttpServer`）：**

| 任務 | Core | 優先級 | 說明 |
|------|------|--------|------|
| `controlTask`（差速/PID/失控保護） | 1 | **5** | 獨佔 Core1，100Hz 控制迴圈，不被相機搶佔 |
| `networkTask`（ESP-NOW 遙測） | 0 | **4** | Core0 上高於相機，遙測不被串流卡住 |
| 相機 HTTP（`esp_http_server`） | 0 | **2** | 釘 Core0、降優先級；送 MJPEG 但讓位給控制/遙測 |
| `streamTask`（相機擷取） | 0 | **1** | 最低，於空檔抓幀 |

> ⚠ **陷阱**：`HTTPD_DEFAULT_CONFIG()` 預設 `task_priority=5` 且 `core_id=tskNO_AFFINITY`。
> 不覆寫的話，相機 HTTP 任務（pri5）會在 **Core1 搶佔 controlTask**、在 **Core0 搶佔 networkTask**，
> 造成操控抖動與遙測延遲。務必 `cfg.core_id=0; cfg.task_priority=2;`。

**airtime 仍是共用頻道**：上述優先級只解決 CPU 搶佔。若實測操控仍因頻寬被串流占滿而延遲，下一段
airtime 槓桿＝在 `streamTask` 對「發佈幀率」設上限（如 ≤15fps）線性降低相機 airtime——不影響 SD
錄影（錄影走 `writeFrame(fb)`，與串流發佈獨立）。**先測再加，避免無謂降畫質。**
